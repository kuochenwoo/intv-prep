# P2 content expansion — 2026-10-15

## Scope

The system-design library expands from five to 15 bilingual scenario seeds, within the requirements document’s suggested expansion range. The original IDs (`url-shortener`, `flash-sale`, `chat`, `activity-feed`, `task-queue`) and their content remain unchanged. Existing cached questions, sessions, notes, Mermaid source and stage drafts remain intact. No database schema, model setting, credential storage or interview prompt is changed.

P2 continues to examine complete architecture, capacity estimates and cross-component trade-offs through the existing five stages and eight-dimension feedback. Each new scenario supplies three functional requirements, two scale assumptions, two reliability constraints and three optional deep dives. These are on-demand generation seeds, not pre-generated tasks, mandatory component choices or claims about production services.

## Authoring review

`content/system-design/review.json` records primary-source references, review boundaries and independent illustrative capacity calculations. It is an authoring aid, not a runtime rubric or a fixed answer shown to the model. Sources describe technical mechanisms; they do not prescribe our traffic figures, SLAs or a canonical architecture. All figures are local training assumptions. Capacity examples use decimal KB/MB/GB/TB, distinguish bits from bytes, and state which overhead is excluded. Candidates can choose different explicit assumptions and defensible architectures.

| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `file-sync`                | At 1m users, 5 changed files/day and 2 MB/file: 10 TB/day of full-file upload before deduplication, retained versions, replication, downloads and metadata. State a changed-byte ratio before claiming delta savings.                                 | Compare content transfer with metadata commit, permissions and conflict handling. Chunk hashes validate content, not access rights; atomic metadata publication does not automatically clean abandoned chunks. HLS is a protocol option, not a required vendor architecture; define cache/revocation boundaries. [source 1](https://www.rfc-editor.org/rfc/rfc8216.html), [source 2](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html)                                                |

| `notification-platform`    | At 10m notifications/day and 3 channels: 30m delivery attempts/day before retries, about 347.2/s average and 3472/s at tenfold peak. One 500-byte status row per logical notification for 30 days is 150 GB; per-channel history is additional.       | Follow accepted work through fan-out queues, providers and callbacks. Do not equate provider acceptance or transport acknowledgement with user receipt; expire stale notifications and bound retries. [source 1](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan)                                                                               |
| `web-crawler`              | At 10m pages/day and 100 KB/page: 1 TB/day, 30 TB for 30 days of compressed pages before replicas, URL metadata and duplicate savings; average fetch rate is about 115.7/s.                                                                           | Connect frontier scheduling, per-site politeness, fetching, parsing and deduplication. Robots rules are not authorization. Revalidate destination safety after DNS resolution and redirects; crawling does not bypass access controls. [source 1](https://www.rfc-editor.org/rfc/rfc9309.html)                                                                                               |
| `metrics-platform`         | At 100k targets, 100 series/target and one sample/15 seconds: about 666667 samples/s. At 16 bytes/sample for 15 days: 13.824 TB raw samples before indexes, WAL, replicas and compression.                                                            | Follow ingestion WAL, series partitions, query aggregation and alert evaluation. Label cardinality multiplies series. The seed uses uncompressed 16-byte samples; published compression observations are not a quota or a universal storage guarantee. [source 1](https://prometheus.io/docs/practices/naming/), [source 2](https://prometheus.io/docs/prometheus/latest/storage/)           |
| `collaborative-editor`     | At 100k active connections and 1 edit/s at 200 bytes: 20 MB/s incoming edit payload, excluding protocol, WAL, snapshots and recipient fan-out. Connection count is not simultaneously active editing count unless assumed.                            | Compare sequencing/OT/CRDT choices without insisting on one. Merge convergence does not provide durable acknowledgement, authorization, transport or presence semantics by itself; design snapshots and offline compatibility. [source 1](https://docs.yjs.dev/api/document-updates), [source 2](https://docs.yjs.dev/getting-started/working-with-shared-types)                             |
| `ride-dispatch`            | At 100k drivers reporting every 3 seconds: about 33333 updates/s and 3.333 MB/s at 100 bytes/update. Seven-day continuous reporting is 2.016 TB raw history, before indexes and replicas.                                                             | Separate approximate spatial candidate lookup from authoritative driver/trip reservation. A spatial index cannot enforce exclusive assignment. Movement, stale locations and expiring reservations cross component boundaries. [source 1](https://redis.io/docs/latest/develop/ai/search-and-query/query/geo-spatial/), [source 2](https://www.postgresql.org/docs/18/transaction-iso.html)  |
| `ticket-booking`           | At 10 simultaneous events each with 10k peak seat-map queries/s: 100k aggregate reads/s. Do not multiply one event peak by all events unless simultaneous openings are an explicit assumption; hold attempts and live holds are different quantities. | Seat holds and confirmation need authoritative transitions; cached maps can lag. Distinguish this from generic flash-sale inventory using individual seats, hold expiry and a late payment-success callback race. Evaluate alternatives without claiming exactly-once external payment. [source 1](https://www.postgresql.org/docs/18/transaction-iso.html)                                  |
| `distributed-rate-limiter` | At 1m decisions/s across 100 gateways: 10k decisions/s/gateway if evenly distributed. A hot tenant producing 10% contributes 100k decisions/s and can dominate one key; aggregate throughput does not guarantee balanced partitions.                  | Compare central atomic counters, sharded budgets and gateway leases. Atomic commands on one Redis instance do not yield exact quotas across regions or after asynchronous failover; explicitly bound overshoot and define partition behavior. [source 1](https://redis.io/docs/latest/commands/incr/)                                                                                        |

The metrics lower-bound example alone produces about 666,667 samples/s and 13.824 TB of uncompressed samples over 15 days. The ride example distinguishes location writes from ride-request and lookup rates. Video capacity distinguishes viewer bandwidth from CDN origin traffic. Ticket booking focuses on individual seat holds and late payment callbacks rather than duplicating generic flash-sale inventory. Rate limiting requires an explicit precision/partition policy rather than assuming both exact global counters and nonblocking partitions.

## Navigation and compatibility

Search matches either-language titles and current-language features/deep dives. A count and explicit empty state show the filtered scope; random selection chooses a different matching scenario when possible, handles a single match, and is disabled for zero matches. The bounded, keyboard-focusable list keeps history accessible. Searching does not generate a question, change the selected scenario, clear drafts or make an API call.

The seed panel now labels scale/SLA figures as local training assumptions and exposes optional architecture deep dives. Existing user-controlled stage transitions, offline reuse and session language/provider pinning remain unchanged. P1 content and the LC library/Judge are untouched.

## Validation

Automated checks cover all 15 bilingual seeds, stable IDs, non-empty scope/scale/reliability/deep-dive text, English isolation and source review coverage for all ten new scenarios. An explicit storage fixture creates 30 language-specific cached questions, reopens the database, then starts each offline and checks the initial requirements-stage guide; this is not presented as real AI generation. Existing P1/P2 state, failure recovery, prompt separation and grading-context tests remain applicable.

```sh
cargo test --manifest-path src-tauri/Cargo.toml --no-default-features --lib --test p1 --test p2
npm run build
npm run tauri build -- --debug --bundles app
```

`live_design_expansion` is an explicit, separately authorized real-provider probe. It generates File Storage/Sync in Chinese, submits scripted answers through all five stages, requests eight-dimension feedback, reopens an isolated temporary database and reuses its cache offline. It then generates Metrics Ingestion/Alerting in English: eight logical online requests total. Internal content-decode retries remain bounded by the shared adapter. It reads the existing `.env` key without changing settings, credentials or application history. The report is `/tmp/intv-p2-expansion-live.json`.

```sh
INTERVIEW_PROVIDER=deepseek INTERVIEW_MODEL=deepseek-flash \
  cargo run --manifest-path src-tauri/Cargo.toml --no-default-features \
  --example live_design_expansion
```

Scripted answers are probe inputs, not evidence of a human’s ability. A successful network workflow is separate from semantic quality review; these checks cannot certify every generated architecture or feedback judgement.
